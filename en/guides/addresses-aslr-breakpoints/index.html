Memory and execution · 2026-10-17

Why addresses change between runs

An address is not a permanent program label

A function address observed in one run may be invalid or refer elsewhere in the next. Operating systems can place executables and libraries at different locations, and rebuilding can change layout inside a module as well. ASLR is one mechanism involved in randomized address placement. A changed address is not by itself evidence of tampering or debugger failure. Establish whether the comparison concerns one execution, separate executions, or different builds before interpreting the numbers.

Name and address breakpoints age differently

For a function-name breakpoint, the debugger uses symbols to resolve the location. An explicit *0xaddress breakpoint names a numeric location that must be verified for the current session. This is useful without symbols but unreliable when copied blindly into another run. DBG Desk does not yet have a module browser or an automatic relative-address recalculation UI. Prefer a meaningful named location when available. When a numeric address is necessary, verify the current instruction and surrounding code before treating it as the old observation point.

Separate module offsets from object addresses

A code offset within the same build can help compare positions even when the module base changes. Do not apply that idea indiscriminately to heap or stack objects. Their addresses depend on allocations, call depth, and other conditions. Record the module and build for code, and the object and lifetime point for data. A bare absolute address provides little help for another execution. Include the route used to find it so that the logical position can be recovered.

Stabilize the reproduction rather than fixing addresses

There is no need to treat disabling address protection as the default answer to inconvenient movement. Consistent inputs, build records, and named breakpoints often reach the same meaningful stop without memorized numbers. Whether randomization is active under a debugger depends on the operating system and settings, so do not assume every address must change either. Trust addresses verified for the current session, and transfer their context whenever comparing sessions.

Write a location with its context

Instead of recording only a hexadecimal number, note the executable, function, and point after entry. If symbols are available, use the function to find the current location again. If the code changed, inspect the new instructions before reusing an old offset. For a data pointer, record allocation size and the event that created the object. A repeatable way to find the position is more valuable than its number alone.

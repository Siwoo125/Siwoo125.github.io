Missing function names and debug symbols

Code and names are different information

An assembly listing can contain instructions even while stack frames show question marks. The executable supplies machine code, but mapping those addresses to functions, source lines, variables, and types requires additional information. A program can run normally without rich debugging data. First distinguish missing names throughout the application from names missing only in an external library. A nameless frame is not, on its own, evidence of a damaged stack. Identify what information is unavailable before deciding what to rebuild or obtain.

Match symbols to the exact build

A matching filename is not enough. Rebuilding after a source change can move functions and change instruction layouts. Symbols from an older binary or a different configuration may produce misleading names or lines. Record the executable path, compiler options, build time, and available build identifiers. For GCC examples, generate information with -g and check whether packaging has stripped it. If symbols are stored separately, also verify that the debugger can locate the matching file. Fixing a search path cannot make unrelated build artifacts compatible.

Check format support

A Windows PDB file is not a guarantee that every GDB build can use it with the same capabilities. The executable format, debug format, and toolchain combination all matter. DBG Desk displays GDB responses and currently has no PDB conversion or symbol-server manager. If a small MinGW-w64 example has names but another program does not, investigate symbol compatibility rather than assuming the browser connection failed. A debugger suited to an MSVC-centered build may be a better choice for that target.

Use the observations that remain

Without symbols, you can still inspect instructions, registers, accessed memory, and some call relationships. Do not expect source variable names or precise source positions. Use addresses verified in the current session and account for changes in a new run. Start with confirmed call, return, read, and write operations rather than assigning guessed names. For your own program, reproducing the same input in a symbol-equipped build may be the quickest next step, while noting whether the build change affects the failure.

Compare paths side by side

Write down both the editor’s project directory and the executable opened by the debugger. Building a new file in build while opening an older desktop copy explains many mismatches. Once corrected, confirm a named breakpoint and a plausible source position. If only one external module lacks names, request that module’s matching information rather than repeatedly rebuilding unrelated code.
